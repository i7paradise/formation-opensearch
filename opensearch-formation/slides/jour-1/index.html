Architecture : les concepts clés

Cluster "formation-opensearch"
├── Nœud 1 (master + data)
│   ├── Index "products"
│   │   ├── Shard P0 ← Document { "name": "MacBook" }
│   │   └── Shard P1 ← Document { "name": "iPhone" }
│   └── Index "stores"
│       └── Shard P0

    └── Index "products"

Cluster → Nœuds → Index → Shards → Documents

Expliquez chaque niveau. "Un cluster, c'est l'ensemble du système. Les nœuds, ce sont les serveurs. Les index sont comme des tables en SQL. Lucene — Le moteur sous le capot

Apache Lucene
  • Bibliothèque Java open source (Apache)
  • Créée en 1999 par Doug Cutting
  • Gère : index inversé, analyse, scoring BM25
  • Bas niveau — API Java uniquement
OpenSearch
  • Couche distribuée au-dessus de Lucene
  • Ajoute : cluster, REST API, réplication, JSON
  • Chaque shard = 1 index Lucene
  • OS 3.x embarque Lucene 10

💡 OpenSearch est à Lucene ce que MySQL est à InnoDB

Analogie clé : "Lucene, c'est le moteur de votre voiture — puissant mais sans carrosserie ni volant. OpenSearch, c'est la voiture complète." Lucene ne sait pas distribuer des données sur plusieurs machines, gérer des pannes réseau ou exposer une API REST. C'est exactement ce qu'OpenSearch apporte. Lucene 10 (dans OS 3.x) a introduit des améliorations importantes sur les index vectoriels (HNSW pour la recherche sémantique). Timing : 5 min. Transition : "Voyons concrètement ce que Lucene fait à l'intérieur de chaque shard."

Lucene — Segments, refresh et merge

Segment
Unité d'index immuable.
Chaque PUT _doc crée un micro-segment.
Refresh (1 s)
Rend les nouveaux docs searchable.
Coûteux — ne pas réduire en prod.
Merge
Lucene fusionne les petits segments en grands.
Améliore les perfs de lecture. 
// Forcer un refresh immédiat (rare — pour les tests)
POST /products/_refresh

// Désactiver le refresh pendant un chargement massif
PUT /products/_settings
{ "index": { "refresh_interval": "-1" } }
Les segments sont IMMUABLES : une suppression ne détruit pas physiquement le document, elle ajoute un marqueur "deleted". Lucene nettoie lors du merge. C'est pourquoi DELETE suivi d'un GET peut encore retourner le document jusqu'au prochain refresh. En indexation massive (Bulk API), désactiver le refresh_interval accélère l'import de 3× à 5×. Timing : 6 min. Transition : "Lucene, c'est clair. Parlons maintenant d'un risque critique en production : le split-brain."

Split-brain — Le cauchemar distribué

⚠️ Scénario : cluster à 2 nœuds, réseau coupé
Nœud A pense que Nœud B est mort → se proclame master
Nœud B pense que Nœud A est mort → se proclame master
→ 2 masters, 2 vérités, données incohérentes
❌ 2 nœuds
Réseau coupé → split-brain
Chaque nœud = 1 vote
Impossible de décider !
✓ 3 nœuds
Réseau coupe 1 + 2
Le groupe de 2 a le quorum
→ Élit le master. Sûr !
Exemple concret : "Imagine deux banques dans un système distribué qui pensent toutes les deux être la référence. Client A dépose 100€ sur nœud A, client B retire 100€ sur nœud B. Les deux opérations réussissent... le compte est à -100€ quand le réseau revient." Le split-brain en production peut corrompre des données irrémédiablement. C'est la raison numéro 1 pour laquelle on ne fait JAMAIS un cluster à 2 nœuds. Timing : 6 min. Transition : "La solution, c'est le quorum — voyons comment ça marche."

Quorum — Pourquoi 3 nœuds minimum ?

Formule du quorum
quorum = ⌊ nb_master_eligible / 2 ⌋ + 1
Nœuds master-eligibleQuorumTolérance aux pannes
110 panne possible ❌
220 panne — split-brain ! ❌
321 panne tolérée ✓
532 pannes tolérées ✓
743 pannes tolérées ✓

💡 Toujours un nombre impair de nœuds master-eligible en production

Avec 3 nœuds : si 1 tombe, 2 restent → quorum atteint → le cluster continue. Si 2 tombent, 1 reste → quorum non atteint → le cluster refuse d'écrire (pour éviter la corruption). Avec 2 nœuds : si 1 tombe, 1 reste mais il lui faut 2 votes → cluster en arrêt. C'est pire que le split-brain ! Ne jamais mettre 2 nœuds master-eligible. Pour la formation jour 3 en cluster, on utilisera exactement 3 nœuds. Timing : 6 min. Transition : "Voyons comment configurer ça dans OpenSearch."

Configuration OpenSearch — Anti-split-brain

# opensearch.yml — nœud 1 sur 3
cluster.name: formation-opensearch
node.name: node-1
node.roles: [ master, data ]

# Découverte des pairs
discovery.seed_hosts:
  - node-1:9300
  - node-2:9300
  - node-3:9300

# CRITIQUE : liste les nœuds master à la création du cluster
# (à supprimer après le premier démarrage)
cluster.initial_master_nodes:
  - node-1
  - node-2
  - node-3
✅ OpenSearch calcule automatiquement le quorum à partir de initial_master_nodes
`cluster.initial_master_nodes` est UNIQUEMENT utilisé au tout premier démarrage du cluster (bootstrap). Une fois le cluster formé, OpenSearch maintient la liste des nœuds master-eligible lui-même. Si on redémarre un cluster existant avec cette config, il l'ignore. Erreur courante en formation : configurer initial_master_nodes mais oublier de mettre les 3 nœuds → le cluster attend indéfiniment. Rappel : le jour 3 on configure exactement ce fichier sur 3 conteneurs Docker. Timing : 5 min. Transition : "Maintenant, vérifiez que vous avez bien compris avec le quiz."

Chapitre 3a

Fonctionnement d'OpenSearch

"Comment OpenSearch trouve-t-il vos documents en quelques millisecondes ?"

Après la pause déjeuner. Faites une petite récap en 2 min. Transition : "L'index inversé, c'est le secret d'OpenSearch."

L'index inversé — le secret de la rapidité

Base SQL (scan séquentiel)

Doc 1: "ordinateur portable léger"
Doc 2: "ordinateur de bureau puissant"
Doc 3: "tablette tactile légère"
→ LIKE '%ordinateur%' = scan complet

Index inversé (lookup direct)

"ordinateur" → [Doc1, Doc2]
"portable"   → [Doc1]
"léger"      → [Doc1, Doc3]
→ Chercher "ordinateur" = 1 lookup
C'est la slide la plus importante du jour 1. Prenez le temps de bien l'expliquer. "Imaginez un annuaire téléphonique : chercher un nom par ordre alphabétique est instantané, chercher un numéro pour trouver le nom serait lent. L'index inversé, c'est l'annuaire optimisé pour la recherche textuelle." Lucene crée et gère ces index inversés. OpenSearch distribue les shards (chaque shard = un index Lucene). Timing : 8 min.

Mappings — Types de champs

PUT /products
{
  "mappings": {
    "properties": {
      "name":           { "type": "text",    "analyzer": "standard" },
      "category":       { "type": "keyword" },
      "price":          { "type": "float" },
      "in_stock":       { "type": "boolean" },
      "created_at":     { "type": "date" },
      "stock_quantity": { "type": "integer" },
      "location":       { "type": "geo_point" },
      "tags":           { "type": "keyword" },
      "description": {
        "type": "text",
        "fields": { "keyword": { "type": "keyword", "ignore_above": 256 } }
      }
    }
  }
}
text = full-text analysé | keyword = valeur exacte (filtre, tri, agrégation)
La distinction text/keyword est CRITIQUE. text : tokenisé, analysé, utilisé pour la recherche full-text ("match"). keyword : valeur exacte, utilisé pour filter (term), tri (sort), agrégation (terms). On peut avoir les deux avec multi-fields. Erreur commune : utiliser "text" sur un champ category et essayer de faire une agrégation dessus → erreur "Fielddata is disabled". Timing : 8 min.

API CRUD

# CREATE — PUT avec ID ou POST sans ID
PUT /products/_doc/1
{ "name": "MacBook Pro", "price": 2499.99, "category": "Électronique" }

# READ
GET /products/_doc/1

# UPDATE — partiel avec _update
POST /products/_update/1
{ "doc": { "price": 2299.99 } }

# DELETE
DELETE /products/_doc/1

# BULK — indexation en masse (action + source par paire)
POST /products/_bulk
{ "index": { "_id": "2" } }
{ "name": "iPhone 15", "price": 999.99 }
{ "index": { "_id": "3" } }
{ "name": "iPad Pro", "price": 1099.99 }
Montrez que PUT avec ID est idempotent (remplace). POST sans ID génère un ID automatique. Le Bulk API est crucial pour la performance : indexer 1 document à la fois est 10-100x plus lent qu'en bulk. Règle : toujours utiliser le Bulk API pour plus de 100 documents. Timing : 8 min.

Query DSL & Agrégations

"Comment exprimer des recherches complexes et analyser vos données ?"

Après la pause de 15h. Timing : 30 secondes.

Query DSL — Les requêtes de base

// match : full-text avec analyse
{ "query": { "match": { "name": "ordinateur portable" } } }

// term : valeur exacte (keyword uniquement)
{ "query": { "term": { "category": "Électronique" } } }

// range : intervalle numérique ou date
{ "query": { "range": { "price": { "gte": 100, "lte": 500 } } } }

// multi_match : chercher dans plusieurs champs à la fois
{ "query": { "multi_match": { "query": "laptop", "fields": ["name", "description"] } } }

// match_all : tous les documents
{ "query": { "match_all": {} } }
La différence match vs term est fondamentale : match analyse la requête (tokenise, lowercase, etc.) avant de chercher. term cherche la valeur exacte. Erreur classique : `{ "term": { "name": "Ordinateur Portable" } }` — ça ne trouve rien car "name" est text donc les tokens sont en minuscules. Pour un champ text, utilisez match. Pour keyword, utilisez term. Timing : 8 min.

Bool Query — Combiner les conditions

POST /products/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "name": "ordinateur" } }
      ],
      "filter": [
        { "term": { "in_stock": true } },
        { "range": { "price": { "lte": 1500 } } }
      ],
      "must_not": [
        { "term": { "category": "Jouets" } }
      ],
      "should": [
        { "term": { "brand": "Apple" } }
      ]
    }
  }
}
must = obligatoire + score | filter = obligatoire sans score (cacheable) | should = bonus score | must_not = exclusion
CRITIQUE : filter est BIEN plus performant que must pour les conditions non-textuelles (boolean, term, range). Pourquoi ? Pas de calcul de score + mise en cache automatique des résultats du filtre. Règle d'or : "Si la condition ne nécessite pas de score, mettez-la dans filter." Timing : 8 min.

Agrégations — Analyser les données

POST /products/_search
{
  "size": 0,
  "aggs": {
    "par_categorie": {
      "terms": { "field": "category", "size": 10 }
    },
    "prix_moyen": {
      "avg": { "field": "price" }
    },
    "histogramme_prix": {
      "histogram": { "field": "price", "interval": 100 }
    }
  }
}
Métriques : avg, sum, min, max, stats, cardinality
Buckets : terms, histogram, date_histogram, range
size: 0 évite de retourner des documents (on veut juste les aggs). Les agrégations peuvent être imbriquées : "Pour chaque catégorie, donne-moi le prix moyen" → terms agg avec avg sub-agg. Le champ doit être de type keyword pour une terms aggregation. Timing : 8 min.

Scoring BM25 — Pourquoi ce résultat en premier ?

# Comprendre le score d'un document
GET /products/_explain/1
{
  "query": { "match": { "name": "ordinateur portable" } }
}

BM25 tient compte de :

  • TF (Term Frequency) : plus le terme apparaît dans le champ, mieux c'est
  • IDF (Inverse Doc Frequency) : les termes rares = plus discriminants
  • Longueur du champ : même terme dans un titre court > dans un texte long
L'API _explain est un outil de debugging essentiel. Elle décompose exactement comment le score a été calculé. Utile quand un document "devrait" apparaître mais n'apparaît pas, ou apparaît trop bas. Timing : 5 min.

Pagination — from/size et search_after

// Pagination classique (limité à 10 000 résultats)
POST /products/_search
{ "from": 0, "size": 20, "query": { "match_all": {} } }

// search_after pour pagination profonde (cursor-based)
POST /products/_search
{
  "size": 20,
  "sort": [{ "price": "desc" }, { "_id": "asc" }],
  "search_after": [999.99, "abc123"]
}
⚠️ from + size > 10 000 → erreur. Utilisez search_after pour la pagination profonde.
La limite de 10 000 résultats par défaut (index.max_result_window) est une protection contre les requêtes coûteuses. search_after utilise le dernier résultat de la page précédente comme curseur — plus efficace que from/size. Timing : 4 min.
