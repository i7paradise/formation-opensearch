Chapitre 4

Fonctionnalités Avancées

"Et si vos recherches comprenaient les déclinaisons du français ?"

Problème : "vélo" ne trouve pas "vélos". "courir" ne trouve pas "couru".

Posez le problème : sans analyseur linguistique, chaque forme d'un mot est un token différent. Le stemming résout ça. Timing : 30 secondes.

Ingest Pipelines — Le principe

Document entrant → Pipeline → Index

Processeurs courants :

lowercaseMet un champ en minuscules
trimSupprime les espaces en début/fin
setDéfinit la valeur d'un champ
removeSupprime un champ
grokParse du texte libre avec des patterns
dateParse et formate des dates
Distinguez pipeline vs analyseur : le pipeline s'exécute UNE FOIS à l'indexation, côté serveur, sur le document entier. L'analyseur s'exécute à l'indexation ET à la recherche, sur un champ text spécifique. Timing : 10 min.

Créer et tester un pipeline

// Créer le pipeline
PUT /_ingest/pipeline/pipeline-produits
{
  "description": "Normalisation produits e-commerce",
  "processors": [
    { "lowercase": { "field": "category" } },
    { "trim": { "field": "description" } },
    { "set": { "field": "indexed_at", "value": "{{_ingest.timestamp}}" } }
  ]
}

// Tester sans indexer
POST /_ingest/pipeline/pipeline-produits/_simulate
{
  "docs": [{
    "_source": {
      "category": "ELECTRONIQUE",
      "description": "   Ordinateur portable   "
    }
  }]
}

// Utiliser le pipeline à l'indexation
PUT /products/_doc/1?pipeline=pipeline-produits
{ "name": "MacBook Pro", "category": "ELECTRONIQUE", "description": "   Super ordi   " }
_simulate est ESSENTIEL. Testez toujours un pipeline avant de l'appliquer en prod — une erreur dans un processor peut corrompre des millions de documents. Montrez la réponse de _simulate : vous voyez le document transformé sans l'avoir indexé. Timing : 12 min.

Chaîne d'analyse — L'ordre compte !

Texte brut → Char Filter → Tokenizer → Token Filters → Tokens 
Entrée : "Vélos électriques d'entrée DE GAMME"

Char Filter (html_strip) : aucun changement
Tokenizer (standard)     : ["Vélos", "électriques", "d", "entrée", "DE", "GAMME"]
lowercase                : ["vélos", "électriques", "d", "entrée", "de", "gamme"]
asciifolding             : ["velos", "electriques", "d", "entree", "de", "gamme"]
french_stop              : ["velos", "electriques", "entree", "gamme"]  (d, de supprimés)
french_stemmer           : ["velo", "electr", "entre", "gamm"]
C'est la slide la plus importante du jour 2. Montrez l'API _analyze en live : POST /products-v2/_analyze avec les différents analyseurs. L'ordre des Token Filters COMPTE : lowercase doit être avant asciifolding sinon "É" ne sera pas normalisé. Timing : 10 min.

Créer un analyseur français personnalisé

PUT /products-v2
{
  "settings": {
    "analysis": {
      "filter": {
        "french_stemmer": { "type": "stemmer", "language": "french" },
        "french_stop": { "type": "stop", "stopwords": "_french_" }
      },
      "analyzer": {
        "french_custom": {
          "type": "custom",
          "tokenizer": "standard",
          "filter": ["lowercase", "asciifolding", "french_stop", "french_stemmer"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "name": { "type": "text", "analyzer": "french_custom" },
      "description": { "type": "text", "analyzer": "french_custom" }
    }
  }
}

// Tester l'analyseur
POST /products-v2/_analyze
{ "analyzer": "french_custom", "text": "Vélos électriques d'entrée de gamme" }
Expliquez que l'analyseur doit être défini AVANT d'indexer des données. Si on le change après, il faut réindexer (les tokens en index ne correspondent plus à la requête). L'API _reindex permet de migrer les données. Timing : 10 min.

Completion Suggester — Autocomplétion

// 1. Mapping — type completion
PUT /products-v2/_mapping
{
  "properties": {
    "name_suggest": { "type": "completion" }
  }
}

// 2. Requête d'autocomplétion
POST /products-v2/_search
{
  "suggest": {
    "produit-suggest": {
      "prefix": "ordi",
      "completion": {
        "field": "name_suggest",
        "size": 5,
        "fuzzy": { "fuzziness": 1 }
      }
    }
  }
}
Le type completion utilise une structure FST (Finite State Transducer) en mémoire — ultra-rapide pour les suggestions.
Le completion suggester est optimisé pour l'autocomplétion préfixe (comme la barre de recherche d'Amazon). Il ne fait PAS d'analyse linguistique — c'est des préfixes exacts. Pour la correction orthographique, utiliser le term suggester. Timing : 7 min.

Highlighting & Recherche Géographique

// Highlighting
POST /products/_search
{
  "query": { "match": { "description": "ordinateur portable" } },
  "highlight": {
    "pre_tags": ["<mark>"], "post_tags": ["</mark>"],
    "fields": { "description": { "fragment_size": 150 } }
  }
}

// Geo distance — magasins à moins de 5km de Paris
POST /stores/_search
{
  "query": {
    "geo_distance": {
      "distance": "5km",
      "location": { "lat": 48.8566, "lon": 2.3522 }
    }
  },
  "sort": [{ "_geo_distance": { "location": { "lat": 48.8566, "lon": 2.3522 }, "order": "asc", "unit": "km" } }]
}
Highlighting : les balises pre_tags/post_tags entourent les termes matchés dans les extraits. Le champ stores.location doit être de type geo_point dans le mapping. Timing : 7 min.

Optimisation — Indexation & Requêtes

⚡ Optimiser l'indexation

  • Utiliser le Bulk API (toujours)
  • refresh_interval: -1 pendant le chargement
  • replicas: 0 pendant le chargement massif
  • dynamic: strict pour éviter le mapping explosion

🔍 Optimiser les requêtes

  • filter au lieu de must (pas de score)
  • _source filtering pour réduire le payload
  • search_after pour la pagination profonde
  • Éviter les wildcard avec leading star (*term)
Le piège du wildcard leading : `*ordinateur` nécessite de scanner tous les termes de l'index inversé. Très coûteux. Utilisez un edge_ngram tokenizer à la place pour les autocomplétion. Le dynamic:strict protège contre un développeur qui envoie accidentellement des champs inconnus qui créent des mappings dynamiques. Timing : 7 min.

Index Patterns & KQL

Index Pattern : Indiquer à Dashboards quels index utiliser

  • Pattern : products ou products-* (wildcard)
  • Champ date : created_at (pour les filtres temporels)
  • Management → Stack Management → Index Patterns → Create

KQL (Kibana Query Language) dans Discover :

category: "Électronique" AND price > 500
in_stock: true AND rating >= 4
name: "ordinateur" OR name: "laptop"
Problème fréquent : KQL est sensible à la casse sur les champs keyword ! "Electronique" ne trouve pas "Électronique". Montrez la différence en live dans Discover. Timing : 8 min.

Choisir la bonne visualisation

VisualisationCas d'usageAgrégation
Bar ChartComparer des catégoriesTerms

Règle de base : si vous voulez COMPARER → Bar Chart. Si vous voulez voir UNE TENDANCE dans le temps → Line Chart. Si vous voulez des PROPORTIONS → Pie (max 7 slices sinon illisible). Si vous voulez voir des DONNÉES SUR UNE CARTE → Coordinate Map. Timing : 8 min.

Construire un Dashboard

  1. Créer chaque visualisation individuellement dans Visualize
  2. Aller dans Dashboard → Create new dashboard
  3. Ajouter les panneaux via "Add an existing" ou "Create new"
  4. Redimensionner et réorganiser par glisser-déposer
  5. Ajouter des filtres globaux (s'appliquent à toutes les viz)
  6. Définir la plage temporelle par défaut
  7. Sauvegarder et partager (Share → Copy link)
Montrez la construction d'un dashboard simple en live. Insistez sur : les filtres globaux affectent toutes les visualisations du dashboard. La plage temporelle dépend du champ date défini dans l'Index Pattern. Timing : 10 min.
