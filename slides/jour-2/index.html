Sécurité OpenSearch

Authentification · Autorisation · Audit

"Qui peut lire quoi dans votre cluster ?"

Posez la question rhétorique et laissez quelques secondes. Timing : 1 min.

Architecture sécurité : AAA

1. Authentification
Qui êtes-vous ? (users internes, LDAP, OIDC)
2. Autorisation
Que pouvez-vous faire ? (rôles, permissions)
3. Audit
Qui a fait quoi ? (logs d'accès)
Security Plugin activé par défaut depuis OpenSearch 1.0.
Toutes les requêtes passent par les 3 couches avant d'atteindre les données.
Le Security Plugin est la première ligne de défense. Sans lui, n'importe qui peut lire ou supprimer vos données. Timing : 5 min.

Utilisateurs internes

}

// LDAP / OIDC : options de configuration dans opensearch.yml
// plugins.security.authc.ldap.http_enabled: true
// → lien avec Active Directory ou Okta
Le mot de passe est stocké en hash bcrypt — jamais en clair. Les backend_roles viennent de LDAP ou OIDC.
Montrez la création en live si possible. Précisez : les users internes sont pratiques en DEV, mais en PROD on préfère LDAP/OIDC (centralisé). Timing : 5 min.

Rôles et permissions — concepts

Niveaux de permissions

  • cluster — ex: cluster:monitor/*
  • index — ex: indices:data/read/*
  • document (DLS) — filtrer par doc
  • field (FLS) — masquer des champs

Hiérarchie

  • Un rôle = ensemble de permissions
  • Un utilisateur → 1+ rôles (role mapping)
  • Les permissions s'accumulent
Insistez sur la hiérarchie : cluster > index > document > field. Le niveau le plus bas (field) est le plus précis. Timing : 5 min.

Créer un rôle custom

PUT /_plugins/_security/api/roles/catalogue_reader
{
  "cluster_permissions": ["cluster:monitor/health"],
  "index_permissions": [{
    "index_patterns": ["products-*"],
    "allowed_actions": [
      "indices:data/read/search",
      "indices:data/read/get",
      "indices:monitor/settings/get"
    ]
  }]
}

// Deny explicite : ne pas autoriser DELETE
// → simplement ne pas inclure l'action DELETE dans allowed_actions
Les index_patterns supportent les wildcards : products-*, logs-2025-*.
Principe du least privilege : on accorde UNIQUEMENT ce qui est nécessaire. Timing : 6 min.

Role Mapping : lier user → rôle

PUT /_plugins/_security/api/rolesmapping/catalogue_reader
{
  "users": ["analyst"],
  "backend_roles": ["ldap_catalogue_team"]
}

// Vérifier le mapping
GET /_plugins/_security/api/rolesmapping/catalogue_reader
2 façons de mapper :
• users → utilisateurs internes directs
• backend_roles → groupes LDAP / rôles OIDC (mapping indirect)
Le mapping par backend_role est le pattern recommandé en production : les groupes LDAP sont gérés par l'infra, pas par OpenSearch. Timing : 5 min.

TLS : sécuriser les communications

# opensearch.yml — TLS transport (nœud ↔ nœud)
plugins.security.ssl.transport.pemcert_filepath: node.pem
plugins.security.ssl.transport.pemkey_filepath:  node-key.pem
plugins.security.ssl.transport.pemtrustedcas_filepath: root-ca.pem
plugins.security.ssl.transport.enforce_hostname_verification: true

# TLS REST (client ↔ cluster)
plugins.security.ssl.http.enabled: true
plugins.security.ssl.http.pemcert_filepath: node.pem
plugins.security.ssl.http.pemkey_filepath:  node-key.pem
⚠️ En prod : certificats signés CA interne, pas self-signed. TLS transport obligatoire pour protéger les données inter-nœuds.
Différenciez transport (réseau interne cluster) et REST (API externe). En formation on utilise self-signed avec -k. En prod, jamais de self-signed. Timing : 6 min.

Document Level Security (DLS)

PUT /_plugins/_security/api/roles/vente_eu
{
  "index_permissions": [{
    "index_patterns": ["products-*"],
    "allowed_actions": ["indices:data/read/search"],
    "dls": "{\"term\": {\"region\": \"EU\"}}"
  }]
}
L'utilisateur voit uniquement les documents qui matchent le filtre DLS.
Impact perf : le filtre DLS s'exécute en filter context → mis en cache, pas de calcul de score.
Le DLS est transparent pour l'utilisateur : il ne sait pas que des documents lui sont cachés. Cas typique : tenant multi-région, données PII. Timing : 6 min.

Field Level Security (FLS)

PUT /_plugins/_security/api/roles/vente_eu
{
  "index_permissions": [{
    "index_patterns": ["products-*"],
    "allowed_actions": ["indices:data/read/search"],
    "fls": ["~cost_price", "~supplier_margin"]
  }]
}
Le préfixe ~ exclut le champ.
Sans ~ = liste blanche (seuls ces champs sont visibles).
Cas : masquer le prix fournisseur à l'équipe commerciale.
FLS est complémentaire au DLS : DLS filtre les lignes, FLS filtre les colonnes. Timing : 6 min.

Exemple e-commerce : DLS + FLS combinés

Rôle sales_eu
DLS : region = "EU"
FLS : cache cost_price, internal_notes
Admin
Voit tous les documents
Voit tous les champs 
// Vue sales_eu sur doc { region: "FR", price: 99, cost_price: 42 }
{
  "_source": { "region": "FR", "price": 99 }
  // cost_price absent ← FLS
  // seuls docs EU ← DLS
}
Montrez le schéma : même document, deux vues différentes selon le rôle. C'est la puissance du RBAC combiné DLS/FLS. Timing : 5 min.

Tenant Isolation

Les tenants sont des espaces Dashboards isolés :

  • global — partagé entre tous
  • private — personnel à chaque utilisateur
  • Tenants custom — par équipe, par département
Chaque tenant a ses propres dashboards, index patterns et visualizations.
Utile pour le multi-équipe : l'équipe produit ne voit pas les dashboards de l'équipe logistique.
Les tenants sont une feature Dashboards uniquement — ils n'impactent pas l'accès aux données (c'est DLS/FLS pour ça). Timing : 4 min.

Audit Logs & bonnes pratiques

# opensearch.yml

Checklist sécurité prod :
  • ✅ TLS obligatoire transport + REST
  • ✅ Least privilege sur chaque rôle
  • ✅ DLS / FLS si données PII ou multi-tenant
  • ✅ Audit activé (RGPD, conformité)
  • ✅ Certificat admin isolé, rotation régulière
L'audit log stocke : qui, quoi, quand, depuis quelle IP. Essentiel pour la conformité RGPD. Timing : 5 min.

Ingest Pipelines

Transformer avant d'indexer

"Et si vos données arrivaient sales ?"

Transition naturelle après la sécurité. Timing : 1 min.

Le principe : document → pipeline → index

Document entrant → Processor 1 → Processor 2 → Index

S'exécute une seule fois à l'indexation, côté serveur.
Différent de l'analyseur (qui s'exécute aussi à la recherche).

PUT /_ingest/pipeline/mon-pipeline
{
  "processors": [
    { "lowercase": { "field": "category" } },            // ← Processor 1
    { "set": { "field": "indexed_at",
               "value": "{{{_ingest.timestamp}}}" } }    // ← Processor 2
  ]
}
// Exécution séquentielle : chaque processor reçoit le doc modifié par le précédent
Bien distinguer : pipeline = transforme le document entier, une fois, à l'indexation. Analyseur = tokenise un champ text, à l'indexation ET à la recherche. Timing : 4 min.

Processors essentiels — pipeline complet

PUT /_ingest/pipeline/nettoyage-produits
{
  "processors": [
    { "lowercase": { "field": "category" } },
    { "trim":      { "field": "description" } },
    { "rename":    { "field": "ts",    "target_field": "@timestamp" } },
    { "convert":   { "field": "price", "type": "float" } },
    { "remove":    { "field": "_tmp",  "ignore_missing": true } },
    { "set":       { "field": "indexed_at", "value": "{{{_ingest.timestamp}}}" } }

}

POST /_ingest/pipeline/nettoyage-produits/_simulate
{ "docs": [{ "_source": { "category": "ELECTRONIQUE", "description": "  Ordi  ",
                           "ts": "2025-01-15", "price": "299.99", "_tmp": "draft" } }] }

// → category:"electronique", description:"Ordi", @timestamp:"2025-01-15", price:299.99
Insister sur _simulate avant tout passage en prod. Timing : 3 min.

Processors avancés — pipeline complet

PUT /_ingest/pipeline/enrichissement-logs
{
  "processors": [
    { "grok":       { "field": "raw",  "patterns": ["%{IP:ip} %{WORD:method} %{URIPATHPARAM:path}"] } },
    { "split":      { "field": "tags", "separator": ","  } },
    { "gsub":       { "field": "phone","pattern": "[^0-9]", "replacement": "" } },
    { "html_strip": { "field": "body" } },
    { "uri_parts":  { "field": "url"  } }
  ]
}

// Entrée  : { "raw":"1.2.3.4 GET /api?q=test", "tags":"prod,fr", "phone":"+33 6 12 34" }
// Sortie  : { "ip":"1.2.3.4", "method":"GET", "path":"/api?q=test",
//             "tags":["prod","fr"], "phone":"3361234" }
Montrer grok + split en combinaison : cas réel logs applicatifs. Timing : 3 min.

_simulate est ESSENTIEL. Une erreur dans un processor peut corrompre des millions de documents. Montrez la réponse _simulate : le document transformé sans l'avoir indexé. Timing : 6 min.

Grok processor : parser des logs

PUT /_ingest/pipeline/nginx-logs
{
  "processors": [{
    "grok": {
      "field": "message",
      "patterns": [
        "%{IP:client} %{WORD:method} %{URIPATHPARAM:request} %{NUMBER:status:int}"
      ]
    }
  }]
}

// Entrée  : "192.168.1.1 GET /api/products?q=ordi 200"
// Sortie  : { "client": "192.168.1.1", "method": "GET",
//             "request": "/api/products?q=ordi", "status": 200 }
Bibliothèque de patterns : /etc/opensearch/patterns/ — ou définir les siens.
grok est la killer feature pour l'ingestion de logs. Les patterns %{IP}, %{NUMBER}, %{WORD} sont prédéfinis. Timing : 6 min.

Date processor : normaliser les formats

PUT /_ingest/pipeline/normalize-dates
{
  "processors": [{
    "date": {
      "field":        "raw_date",
      "formats":      ["dd/MM/yyyy", "MM/dd/yyyy", "ISO8601"],
      "target_field": "@timestamp",
      "timezone":     "Europe/Paris"
    }
  }]
}

// "15/01/2025" → "@timestamp": "2025-01-15T00:00:00.000Z"
// "01/15/2025" → "@timestamp": "2025-01-15T00:00:00.000Z"
⚠️ Toujours préciser le timezone — sinon UTC par défaut → décalage de 1h/2h en France.
Le date processor est indispensable dès qu'on ingère des données horodatées venant de sources différentes. Timing : 5 min.

On_failure handler : gérer les erreurs

PUT /_ingest/pipeline/pipeline-robuste
{
  "processors": [{
    "grok": {
      "field": "message",
      "patterns": ["%{IP:client} %{WORD:method}"],
      "on_failure": [{
        "set": {
          "field":  "_index",
          "value":  "failed-docs"
        }
      }]
    }
  }]
}
Sans on_failure : le document est rejeté silencieusement.
Pattern prod : router les docs en erreur vers un index dédié pour inspection.
Ne jamais laisser un pipeline sans on_failure en production — vous perdrez des données sans vous en rendre compte. Timing : 5 min.

Processors conditionnels : if Painless

PUT /_ingest/pipeline/pipeline-premium
{
  "processors": [{
    "set": {
      "if":    "ctx.price != null && ctx.price > 1000",
      "field": "segment",
      "value": "premium"
    }
  }, {
    "remove": {
      "if":    "ctx.containsKey('_tmp')",
      "field": "_tmp"
    }
  }]
}
Painless est compilé → performances acceptables. Ne pas y mettre de logique métier complexe.
Le if Painless permet d'éviter plusieurs pipelines distincts. Mais si la logique devient complexe, mieux vaut la mettre en amont (dans le client). Timing : 5 min.

default_pipeline et final_pipeline

// Appliquer automatiquement à tout nouvel index
PUT /products/_settings
{
  "index.default_pipeline": "pipeline-produits"
}

// final_pipeline s'exécute EN DERNIER,
// même si le document spécifie un autre pipeline
PUT /products/_settings
{
  "index.final_pipeline": "audit-pipeline"
}
default_pipeline — appliqué si aucun pipeline spécifié dans la requête d'indexation.
final_pipeline — toujours exécuté en dernier (ex: enrichissement, audit).
Cas concret : final_pipeline pour ajouter indexed_at sur tous les docs quel que soit le pipeline utilisé. Timing : 5 min.

Analyse du texte

Pourquoi "vélos" ≠ "velo" ?

"La recherche plein texte commence ici."

Transition depuis les pipelines. Dites : "On vient de voir comment transformer les données à l'indexation. Maintenant on va voir comment OpenSearch comprend le texte." Timing : 1 min.

Chaîne d'analyse : Char Filter → Tokenizer → Token Filters

Texte brut → Char Filter → Tokenizer → Token Filters → Tokens finaux 
Entrée          : "Vélos électriques d'ENTRÉE DE GAMME"
Tokenizer       : ["Vélos", "électriques", "d", "ENTRÉE", "DE", "GAMME"]
lowercase       : ["vélos", "électriques", "d", "entrée", "de", "gamme"]
asciifolding    : ["velos", "electriques", "d", "entree", "de", "gamme"]
french_stop     : ["velos", "electriques", "entree", "gamme"]
french_stemmer  : ["velo", "electr", "entre", "gamm"]
L'ordre des filtres COMPTE : lowercase AVANT asciifolding sinon "É" n'est pas normalisé. Montrez _analyze en live. Timing : 6 min.

Tokenizers : standard, whitespace, ngram, edge_ngram

TokenizerTokens de "ordi-portable"Cas d'usage
standard["ordi", "portable"]Texte général
whitespace["ordi-portable"]Codes produits
ngram (2-3)["or","rd","di","po","or"...]Recherche substring
edge_ngram (2-6)["or","ord","ordi"...]Autocomplétion préfixe
⚠️ ngram et edge_ngram augmentent significativement l'espace disque de l'index.
edge_ngram est le choix standard pour l'autocomplétion. ngram pour la recherche au milieu d'un mot (coûteux). Timing : 5 min.

Token Filters : lowercase, asciifolding, stop, stemmer, synonym

FilterTransformation
lowercase"ORDI" → "ordi"
asciifolding"Vélo" → "Velo" (après lowercase)
stop["de", "le", "un"] → supprimés
stemmer (french)"électriques" → "electr"
synonym"ordi" → "ordinateur"
💡 Ordre critique : lowercase AVANT asciifolding — sinon "É" majuscule n'est pas normalisé.
Timing : 5 min.

Créer un analyseur français personnalisé

PUT /products-v2
{
  "settings": {
    "analysis": {
      "filter": {
        "french_stemmer": { "type": "stemmer",  "language": "french" },
        "french_stop":    { "type": "stop",     "stopwords": "_french_" }
      },
      "analyzer": {
        "french_custom": {
          "type":      "custom",
          "tokenizer": "standard",
          "filter":    ["lowercase", "asciifolding", "french_stop", "french_stemmer"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "name":        { "type": "text", "analyzer": "french_custom" },
      "description": { "type": "text", "analyzer": "french_custom" }
    }
  }
}
L'analyseur doit être défini AVANT d'indexer des données. Si on le change après, il faut _reindexer. Timing : 7 min.

API _analyze : tester et déboguer

// Tester l'analyseur sur un texte
POST /products-v2/_analyze
{
  "analyzer": "french_custom",
  "text":     "Vélos électriques d'entrée de gamme"
}
// → tokens : ["velo", "electr", "entre", "gamm"]

// Comparer avec l'analyseur standard
POST /products-v2/_analyze
{
  "analyzer": "standard",
  "text":     "Vélos électriques d'entrée de gamme"
}
// → tokens : ["vélos", "électriques", "d", "entrée", "de", "gamme"]
La réponse inclut : tokens + positions + offsets — très utile pour déboguer des requêtes qui ne trouvent rien.
Montrez la différence côte à côte. C'est la démo la plus "aha moment" de la journée : on voit exactement pourquoi "vélo" trouve "vélos". Timing : 5 min.

Multi-fields : keyword + text sur le même champ

PUT /products-v2/_mapping
{
  "properties": {
    "name": {
      "type":     "text",
      "analyzer": "french_custom",
      "fields": {
        "raw": { "type": "keyword" }
      }
    }
  }
}

// Recherche full-text  → products-v2.name
// Sort / agrégation   → products-v2.name.raw
Stocké une seule fois, indexé deux façons. Pas de duplication de données.
Pattern très courant : champ name analysé pour la recherche, name.raw keyword pour le tri et les agrégations. Timing : 5 min.

Analyseur à l'indexation vs à la recherche

"name_suggest": {
  "type":           "text",
  "analyzer":       "edge_ngram_analyzer",  // indexation : génère les préfixes
  "search_analyzer": "standard"             // recherche  : ne pas découper le préfixe
}

Cas autocomplétion :

  • Indexation avec edge_ngram → stocke "or", "ord", "ordi", "ordin"…
  • Recherche avec standard → cherche le token exact saisi ("ordi")
  • Résultat : "ordi" matche "ordinateur" sans sur-matching
Si on utilisait edge_ngram aussi à la recherche, "ordi" serait découpé en "or","rd","di" → trop de faux positifs. Timing : 5 min.

Changer d'analyseur impose un _reindex

Les tokens stockés dans l'index inversé ne sont pas recalculés automatiquement quand on modifie l'analyseur.

Workflow obligatoire :
1. Créer products-v2 avec le nouveau mapping + analyseur
2. POST /_reindex pour migrer les données
3. Swap d'alias → zéro downtime

→ Transition naturelle vers l'après-midi : l'API _reindex en détail.

C'est la slide de transition matin/après-midi. Insistez : dans un système en production, tout changement de mapping ou d'analyseur passe par _reindex + alias swap. C'est pour ça qu'on y consacre une section complète cet après-midi. Timing : 5 min.

Architecture Cluster

Les internals OpenSearch

"Comment OpenSearch distribue vos données sur 3+ machines ?"

Reprise après le déjeuner. Faites un point d'énergie. Timing : 1 min.

Lucene internals : segments et inverted index

  • Un index Lucene = ensemble de segments immutables
  • Inverted index : terme → liste de doc IDs (comme l'index d'un livre)
  • Refresh (1s, in-memory) : rend les docs visibles sans garantie durabilité
  • Flush : écrit sur disque + créé un commit point (durabilité garantie)
  • Merge : fusionne les petits segments périodiquement
Un shard OpenSearch = une instance Lucene complète.
Les segments immutables expliquent pourquoi les updates sont en réalité delete + index. Le merge en arrière-plan nettoie les segments marqués deleted. Timing : 6 min.

De Lucene à OpenSearch : shard = instance Lucene

1 shard primaire = 1 index Lucene indépendant.
OpenSearch orchestre N shards sur M nœuds.

Cluster 3 nœuds, index "products" (2 shards primaires, 1 replica) :

Nœud 1 : P0 + R1
Nœud 2 : P1 + R0
Nœud 3 : (coordinating + replicas overflow)

P = primary, R = replica
Insistez : primary et replica du même shard ne sont JAMAIS sur le même nœud. OpenSearch le garantit automatiquement. Timing : 4 min.

Les nœuds master dédiés sont légers : 2-4 Go RAM suffit. Ce sont les data nodes qui ont besoin de resources. Timing : 4 min.

Split-brain et quorum : pourquoi 3 nœuds minimum

❌ 2 nœuds
Réseau coupé → 2 masters
→ données incohérentes
✓ 3 nœuds
Si 1 tombe : 2 restants = quorum
→ cluster continue
Formule : quorum = ⌊N/2⌋ + 1

N master-eligibleQuorumTolérance
110 panne ❌
22split-brain ❌
321 panne ✓
532 pannes ✓
Toujours impair en prod. Avec 2 nœuds : si 1 tombe, l'autre n'a pas le quorum → cluster bloqué (pire que split-brain). Timing : 6 min.

Réplication : primary + replica

Écriture : toujours vers le primary → propagé aux replicas de façon synchrone.

Lecture : load balance sur tous les shards (primary + replicas).

✅ number_of_replicas: 1 minimum en production.
✅ Augmenter les replicas = scale lecture sans _reindex.
⚠️ Replica ≠ backup — les replicas sont affectés par les mêmes suppressions accidentelles que les primaries.
La distinction replica vs backup est importante : si quelqu'un fait DELETE /products/*, les replicas sont aussi effacés. Les snapshots sont le vrai backup. Timing : 5 min.

Sizing des Shards

La brique fondamentale

"Combien de shards pour votre use case ?"

Timing : 1 min.

Qu'est-ce qu'un shard ? Lifecycle

Un shard est à la fois une unité de distribution ET de parallélisme.

Lifecycle :
Création → segments Lucene → merges périodiques → suppression
⚠️ Le nombre de shards primaires est figé à la création de l'index.
Pour le changer : _reindex obligatoire.
Cette contrainte (shards figés) est la raison pour laquelle il faut bien penser le sizing avant. Timing : 5 min.

Primary vs Replica : écriture vs lecture

Primary shards
• Reçoivent toutes les écritures
• Nombre fixé à la création
• Augmenter = scale écriture
• Nécessite _reindex
Replica shards
• Partagent les lectures
• Modifiable à chaud
• Augmenter = scale lecture
• Pas besoin de _reindex
Key insight : seul le nombre de replicas est modifiable à chaud. Pour l'écriture, on doit anticiper le sizing. Timing : 5 min.

Règle de base : 10–50 GB par shard

Trop petit
< 1 GB
Overhead JVM + Lucene
Trop de threads
Idéal
~30 GB
Cible recommandée
Merges et recovery rapides
Trop grand
> 50 GB
Merges lents
Recovery très long
La règle des 50 GB vient de l'expérience de nombreuses équipes en production. Au-delà, le recovery après une panne peut prendre 30+ minutes. Timing : 4 min.

Sur-sharding : les pièges

Chaque shard = threads JVM + heap + file descriptors.

1000 shards sur 3 nœuds → instabilité, GC pauses, OOM.

Règle : max ~20 shards / Go de RAM heap.

GET /_cluster/stats
// → .indices.shards.total  : nombre total de shards dans le cluster
Le sur-sharding est l'erreur la plus fréquente. Des équipes créent 5 shards par index par défaut, accumulent 200 index, se retrouvent avec 1000 shards. Timing : 5 min.

Calcul pour l'écriture : sizing par throughput

nb_primary_shards = write_throughput_peak / throughput_per_shard

Benchmark typique : 1 shard ≈ 5 000 – 10 000 docs/s selon la taille du document.

Exemple :
Pic d'écriture : 50 000 docs/s
1 shard ≈ 7 000 docs/s
→ 7-8 shards primaires
Le benchmark de 5-10k docs/s est indicatif. En pratique : benchmarkez sur votre matériel avec vos données réelles. Timing : 6 min.

Calcul pour la lecture : sizing par volume

nb_primary_shards = total_data_GB / target_shard_size_GB
Exemple :
Volume total : 300 GB
Cible par shard : 30 GB
→ 10 shards primaires

Anticiper 3 ans de croissance : 300 GB × 3 = 900 GB → 30 shards → peut-être mieux penser à de l'ILM/rollover
Pour les données temporelles (logs), l'ILM (Index Lifecycle Management) résout mieux le problème de croissance que le sur-sizing. Timing : 6 min.

Exercice live : sizing catalogue e-commerce

Données :

  • 200 millions de produits × 2 Ko = 400 Go
  • Pic d'écriture : 20 000 docs/s

Calculer ensemble :

  • nb_primary_shards (écriture → 3, volume → 14, choix ?)
  • nb_replicas (HA + scale lecture)
  • Nombre de nœuds minimum
Plusieurs réponses valides selon la priorité lecture/écriture.
Faites cet exercice de façon interactive. Demandez aux participants de proposer leurs calculs. Pas de bonne/mauvaise réponse unique — c'est un trade-off. Timing : 7 min.

Shard allocation awareness : topologie rack/AZ

# opensearch.yml — déclarer l'attribut du nœud
node.attr.rack: rack1          # ou az: eu-west-1a

# Configuration cluster
cluster.routing.allocation.awareness.attributes: rack
// OpenSearch garantit que primary et replica
// sont sur des racks différents
GET /_cat/shards?v  // → vérifier la distribution
Si rack1 tombe : tous les primaries de rack1 ont leur replica sur rack2 → aucune perte de données.
Timing : 5 min.

Forced awareness : garantir la résilience

# opensearch.yml
cluster.routing.allocation.awareness.force.rack.values: rack1,rack2,rack3

Sans forced awareness : si rack2 tombe, OpenSearch peut surcharger rack1 avec des replicas supplémentaires.

Avec forced awareness : le cluster reste Yellow plutôt que de surcharger les racks survivants.
→ Comportement prévisible, pas de surcharge mémoire inattendue.
Timing : 4 min.

Checklist sizing production

  • ☑ Taille shard < 50 GB
  • ☑ Max 20 shards / Go de RAM heap
  • ☑ Replicas ≥ 1 (HA + scale lecture)
  • ☑ Awareness si multi-rack / multi-AZ
  • ☑ Anticiper 3 ans de croissance (ou utiliser rollover/ILM)
  • ☑ Benchmarker avec des données réelles avant prod
Cette checklist est à afficher dans votre runbook de mise en production. Timing : 5 min.

Resharding et migration

Syntaxe de base : POST _reindex

POST /_reindex
{
  "source": { "index": "products" },

}

// Réponse
{

  "created": 1000,
  "updated": 0,
  "failed":  0,
  "failures": []
}

// Ignorer les conflits de version
POST /_reindex
{
  "conflicts": "proceed",
  "source": { "index": "products" },
  "dest":   { "index": "products-v2", "op_type": "create" }
}
Timing : 5 min.

_reindex avec query filter

// Migrer uniquement les produits EU
POST /_reindex
{
  "source": {
    "index": "products",
    "query": {
      "term": { "region": "EU" }
    }
  },
  "dest": { "index": "products-eu" }
}

// Cas : splitter un index trop gros par région
// products → products-eu + products-us + products-asia
La query dans source est une requête OpenSearch standard — supports bool, range, term, etc.
Timing : 5 min.

_reindex avec script Painless

POST /_reindex
{
  "source": { "index": "products" },
  "dest":   { "index": "products-v2" },
  "script": {
    "source": """
      ctx._source.price_eur    = ctx._source.price * 1.1;
      ctx._source.migrated_at  = params.ts;
      ctx._source.remove('old_field');
    """,
    "params": { "ts": "2025-01-01T00:00:00Z" }
  }
}
Le script Painless peut : renommer un champ, calculer une valeur, supprimer un champ, changer l'index de destination (ctx._index).
Timing : 6 min.

Mode async + suivi avec _tasks

# Démarrer en asynchrone
POST /_reindex?wait_for_completion=false
{
  "source": { "index": "products" },
  "dest":   { "index": "products-v2" }
}
# → { "task": "oTUltX4IQMOUUVeiohTt8A:12345" }

# Suivre la progression
GET /_tasks/oTUltX4IQMOUUVeiohTt8A:12345

# Annuler
POST /_tasks/oTUltX4IQMOUUVeiohTt8A:12345/_cancel

# Lister toutes les tâches reindex en cours
GET /_cat/tasks?v&actions=*reindex
Recommandé pour les volumes >100M documents.
En mode synchrone, le timeout HTTP peut couper la connexion avant la fin du reindex. En mode async, la tâche continue même si la connexion est perdue. Timing : 5 min.

Paramètres avancés : slices, scroll, size

POST /_reindex
{
  "source": {
    "index": "products",
    "size":  1000
  },
  "dest":   { "index": "products-v2" },
  "slices": "auto"
}

// slices: "auto" → 1 slice par shard primaire source
// Parallélise le reindex → divise le temps proportionnellement
//
// size : batch size par scroll (défaut 1000)
// _source filtering : migrer seulement certains champs
// "source": { "_source": ["name", "price", "category"] }
✅ slices: "auto" est le paramètre le plus impactant sur les performances.
Timing : 7 min.

Zero-downtime avec aliases : blue-green reindex

// 1. products-v1 actif via alias "products"
POST /_aliases
{ "actions": [{ "add": { "index": "products-v1", "alias": "products" } }] }

// 2. Créer products-v2 + _reindex (en parallèle du trafic)
POST /_reindex
{ "source": { "index": "products-v1" }, "dest": { "index": "products-v2" } }

// 3. Swap atomique ← zéro interruption de service
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v1", "alias": "products" } },
    { "add":    { "index": "products-v2", "alias": "products" } }
  ]
}

// 4. Supprimer products-v1 après validation
DELETE /products-v1
Le swap atomique est la technique incontournable en production. Les clients continuent de requêter l'alias "products" sans interruption. Timing : 8 min.

Routage des Données

Contrôler où vont vos documents

"Par défaut, OpenSearch distribue au hasard. Vous pouvez faire mieux."

Timing : 1 min.

Routage par défaut : hash(_id)

shard = hash(_id) % number_of_primary_shards

C'est pour ça que le shard count est figé à la création :

  • Si on changeait le nombre de shards, les docs existants seraient sur les mauvais shards
  • Les requêtes GET par _id ne trouveraient plus les documents
  • → _reindex obligatoire pour recalculer la distribution
Ce slide explique enfin POURQUOI on ne peut pas modifier le shard count. C'est une contrainte de l'algorithme de routage. Timing : 5 min.

Custom routing : définir à l'indexation

# Indexer tous les produits électronique → même shard
PUT /products/_doc/1?routing=electronics
{ "name": "iPhone 15", "category": "electronics", "region": "EU" }

PUT /products/_doc/2?routing=electronics
{ "name": "MacBook Pro", "category": "electronics", "region": "US" }

# Observer la distribution
GET /_cat/shards/products?v
Cas d'usage : co-localiser les documents d'un même tenant, d'une même catégorie, ou d'une même région sur le même shard.
Montrez _cat/shards avant/après. Avec le routing forcé, tous les docs "electronics" sont sur le même shard. Timing : 6 min.

Custom routing : requêtes ciblées

# Sans routing : scatter-gather sur TOUS les shards
GET /products/_search
{ "query": { "term": { "category": "electronics" } } }

# Avec routing : va UNIQUEMENT vers le shard "electronics"
GET /products/_search?routing=electronics
{ "query": { "term": { "category": "electronics" } } }

Impact latence : requête ciblée → 1 shard sollicité au lieu de N.
Sur un grand cluster : réduction de latence proportionnelle au nombre de shards évités.

C'est le gain principal du custom routing : transformer un scatter-gather N-shard en une requête mono-shard. Timing : 6 min.

Required routing : forcer le routing

PUT /products/_mapping
{
  "routing": { "required": true }
}

// Sans ?routing= → erreur explicite
PUT /products/_doc/42
{ "name": "Ordi" }
// → 400 Bad Request: routing is required for [products]/[_doc]/[42]

// Avec routing → OK
PUT /products/_doc/42?routing=electronics
{ "name": "Ordi" }
Garantit que personne n'oublie accidentellement le routing lors de l'indexation.
Required routing est une bonne pratique dans les architectures multi-tenant. Timing : 5 min.

Custom routing + bonnes pratiques

Cas typique prod : SaaS multi-tenant — routing par tenant_id.

Avantages
• Requêtes tenant isolées
• Latence réduite
• Isolation CPU des tenants
Risques
• Tenants inégaux → hot shards
• Cardinalité faible → déséquilibre
• Distribution uniforme requise

Combo prod idéal : routing + allocation awareness = co-localisation et résilience multi-AZ.

Le hot shard est le piège : si 1 tenant représente 80% du volume, son shard sera surchargé. Recommandé : valeurs de haute cardinalité avec distribution uniforme. Timing : 8 min.
