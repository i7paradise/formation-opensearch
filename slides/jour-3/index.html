Chapitre 6

Configuration du Cluster

"Et si votre serveur tombait en pleine vente flash ?"

Single point of failure → Cluster haute disponibilité

Posez le problème : un seul nœud = si le serveur meurt, 0 disponibilité. Avec 3 nœuds + replicas, on peut perdre 1 nœud sans interruption. Timing : 30 secondes.

Rôles des nœuds

RôleResponsabilitéRecommandation
masterGestion cluster state, électionDédié si > 5 nœuds
dataStockage, indexation, rechercheLe plus nombreux
ingestExécution des pipelinesOptionnel dédié
coordinatingRouting des requêtesTous les nœuds par défaut
 
# opensearch.yml — rôles d'un nœud
node.roles: [master, data, ingest]
En petits clusters (3 nœuds de formation), chaque nœud joue tous les rôles. En production avec > 5 nœuds, on dédie des nœuds master (3 au minimum) pour éviter qu'un nœud master surchargé cause des problèmes de cluster state. Timing : 8 min.

Discovery & Quorum — Éviter le split-brain

# opensearch.yml
cluster.initial_master_nodes:
  - "opensearch-node1"
  - "opensearch-node2"
  - "opensearch-node3"

discovery.seed_hosts:
  - "opensearch-node1:9300"
  - "opensearch-node2:9300"
  - "opensearch-node3:9300"

Quorum = ⌊N/2⌋ + 1

3 nœuds master-eligibleQuorum = 2 — perd 1 nœud ✅
2 nœuds master-eligibleQuorum = 2 — perd 0 nœud ❌ (split-brain !)
5 nœuds master-eligibleQuorum = 3 — perd 2 nœuds ✅

⚠️ JAMAIS 2 nœuds master-eligible — risque de split-brain !

Le split-brain : si le réseau se partitionne en 2 groupes de 1 nœud chacun (avec 2 nœuds master-eligible), les deux groupes pensent être le master. On se retrouve avec 2 clusters qui divergent. Avec 3 nœuds, même si 1 est isolé, les 2 autres forment un quorum et continuent. cluster.initial_master_nodes n'est utilisé qu'AU PREMIER DÉMARRAGE du cluster — à retirer ensuite ! Timing : 10 min.

Shards — Stratégie de sizing

Primary Shards ⚠️

  • Fixés à la création (immuable !)
  • Règle : 10–50 GB par shard
  • Formule : total_size / 30 GB
  • Trop de petits shards = overhead

Replica Shards 🔄

  • Modifiables à tout moment
  • 1 replica minimum en prod
  • Augmente la disponibilité et les lectures
  • Replica ≠ backup (suppression = sur toutes)
# Routing : hash(_id) % number_of_primary_shards
# Routing personnalisé
PUT /products/_doc/1?routing=category_electronics
{ "name": "iPhone", "category": "Électronique" }
Le fait que primary shards soit immuable est la source de NOMBREUSES erreurs de débutants. Si on crée un index avec 1 shard et qu'il grossit à 500 GB, il faut absolument reindexer. Règle de formation : "Planifiez en pensant à la taille dans 2 ans." Timing : 8 min.

Aliases & Index Templates

// Basculement sans downtime (atomique)
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products-v1", "alias": "products" } },
    { "add":    { "index": "products-v2", "alias": "products" } }
  ]
}

// Index Template pour products-*
PUT /_index_template/products-template
{
  "index_patterns": ["products-*"],
  "template": {
    "settings": { "number_of_replicas": 1, "number_of_shards": 2 },
    "mappings": {
      "properties": {
        "price": { "type": "float" },
        "category": { "type": "keyword" }
      }
    },
    "aliases": { "all-products": {} }
  },
  "priority": 10
}
Les aliases sont l'outil le plus important pour les opérations sans downtime. L'opération `_aliases` avec plusieurs actions est ATOMIQUE — les clients voient soit v1 soit v2, jamais les deux ou aucun. Les Index Templates s'appliquent automatiquement aux nouveaux index qui matchent le pattern. Timing : 8 min.

Snapshots — Sauvegardes incrémentielles

# 1. Créer un repository
PUT /_snapshot/backup-fs
{
  "type": "fs",
  "settings": { "location": "/mnt/snapshots" }
}

# 2. Prendre un snapshot
PUT /_snapshot/backup-fs/snapshot-2026-05-06
{
  "indices": "products,stores",
  "ignore_unavailable": true
}

# 3. Lister les snapshots
GET /_snapshot/backup-fs/_all

# 4. Restaurer
POST /_snapshot/backup-fs/snapshot-2026-05-06/_restore
{ "indices": "products", "rename_pattern": "(.*)", "rename_replacement": "$1-restored" }
Repositories : fs (local/NFS), S3, Azure Blob, GCS
Les snapshots sont INCRÉMENTIELS : seuls les segments Lucene modifiés depuis le dernier snapshot sont copiés. Testez toujours la restauration en pré-prod ! Le repository doit être accessible par TOUS les nœuds. En prod : snapshot quotidien vers S3, rétention 30 jours. Timing : 10 min.

ISM — Index State Management

PUT /_plugins/_ism/policies/logs-lifecycle
{
  "policy": {
    "description": "Lifecycle logs : hot 30 jours puis suppression",
    "default_state": "hot",
    "states": [
      {
        "name": "hot",
        "actions": [],
        "transitions": [{
          "state_name": "delete",
          "conditions": { "min_index_age": "30d" }
        }]
      },
      {
        "name": "delete",
        "actions": [{ "delete": {} }],
        "transitions": []
      }
    ],
    "ism_template": [{
      "index_patterns": ["logs-*"],
      "priority": 100
    }]
  }
}
ISM est parfait pour les logs : les données récentes sont dans l'état "hot", après 30 jours elles sont supprimées automatiquement. Évite que les logs remplissent le disque. Rollover : lorsqu'un index atteint une taille (ex: 50GB) ou un âge, ISM crée automatiquement un nouvel index. Timing : 10 min.

{

_cluster/allocation/explain est l'outil le plus utile en cas de cluster rouge/jaune. Il dit exactement pourquoi un shard n'est pas assigné : disque plein, nœud absent, max_shards_per_node dépassé. Timing : 8 min.

Chapitre 8

Sécurité dans OpenSearch

"Et si quelqu'un accédait à vos données sans autorisation ?"

Le chapitre le plus "sérieux". Expliquez que la sécurité dans OpenSearch est native et gratuite — contrairement à Elasticsearch qui la vendait sous licence. Timing : 30 secondes.

TLS/SSL — Deux couches

🔒 Couche Transport (port 9300)
Entre nœuds du cluster
Chiffre : réplication shards, cluster state
Certificat : node certificate
🌐 Couche REST (port 9200)
Entre clients et cluster
Chiffre : toutes les requêtes API
Certificat : HTTP certificate 
# Avec TLS activé, utiliser -k ou spécifier le CA
curl -k -u admin:Admin@1234! https://localhost:9200/_cluster/health
Pour la formation, on utilise les demo certificates (déjà dans le conteneur OpenSearch). En PRODUCTION : n'utilisez jamais les demo certs — elles sont dans le repo GitHub, tout le monde connaît les clés privées ! Utilisez Let's Encrypt ou un CA interne. Timing : 8 min.

Authentification & RBAC

# Créer un rôle products_reader
PUT /_plugins/_security/api/roles/products_reader
{
  "cluster_permissions": ["cluster_monitor"],
  "index_permissions": [{
    "index_patterns": ["products-*"],
    "allowed_actions": ["read", "indices:data/read/search", "indices:data/read/get"]
  }]
}

# Créer un utilisateur analyst
PUT /_plugins/_security/api/internalusers/analyst
{
  "password": "Analyst@1234!",
  "backend_roles": [],
  "attributes": { "department": "analytics" }
}

# Mapper l'utilisateur au rôle
PUT /_plugins/_security/api/rolesmapping/products_reader
{
  "users": ["analyst"]
}

# Tester : analyst peut lire mais pas écrire
curl -k -u analyst:Analyst@1234! https://localhost:9200/products/_search
curl -k -u analyst:Analyst@1234! -X DELETE https://localhost:9200/products  # → 403
Principes du RBAC : Roles + Permissions → Users. Les rôles built-in utiles : readall (lecture sur tous les index), kibana_user (accès Dashboards), all_access (administrateur). Principe du moindre privilège : donnez uniquement les permissions nécessaires. Timing : 10 min.

DLS & FLS — Sécurité granulaire

// DLS : analyst ne voit que la catégorie Électronique
PUT /_plugins/_security/api/roles/analyst_electronics
{
  "index_permissions": [{
    "index_patterns": ["products-*"],
    "dls": "{ \"term\": { \"category\": \"Électronique\" } }",
    "fls": ["~price", "~original_price"],
    "allowed_actions": ["read"]
  }]
}
// DLS = Document Level Security : filtre les documents visibles
// FLS = Field Level Security : ~ préfixe = exclure ce champ
DLS : Ajoute un filtre de requête → l'utilisateur ne voit que ses documents
FLS : Masque des champs dans la réponse → l'utilisateur ne voit pas certains champs
DLS est parfait pour les données multi-tenant : chaque client ne voit que ses données. FLS pour la conformité RGPD : masquer les données personnelles selon le rôle. Attention : DLS a un coût de performance (filtre ajouté à chaque requête). Timing : 8 min.

Audit Logging — Traçabilité

Catégories d'événements :

GRANTED_PRIVILEGESAccès autorisé
FAILED_LOGINAuthentification échouée
MISSING_PRIVILEGESPermission refusée (403)
SSL_EXCEPTIONProblème TLS
 
# opensearch.yml
plugins.security.audit.type: internal_opensearch
plugins.security.audit.config.enabled_rest_categories:
  - FAILED_LOGIN
  - MISSING_PRIVILEGES
  - GRANTED_PRIVILEGES

Obligatoire pour la conformité RGPD, PCI-DSS, HIPAA

L'audit logging enregistre qui a accédé à quoi et quand. Les logs d'audit sont stockés dans un index dédié (opensearch-security-auditlog-*). Timing : 5 min.
