Récap Jour 2 — 6 questions

  1. Différence DLS vs FLS ?
  2. Pourquoi changer d'analyseur impose _reindex ?
  3. Formule quorum pour N nœuds master-eligible ?
  4. Que fait _reindex?wait_for_completion=false ?
  5. Différence hash(_id) vs custom routing ?
  6. À quoi sert index.default_pipeline ?
Réponses : 1) DLS = filtrage au niveau des documents (certains docs invisibles), FLS = filtrage au niveau des champs (certains champs masqués dans un doc visible. 2) L'index inversé existant est déjà tokenisé selon l'ancien analyseur — il faut recréer l'index et réindexer tous les documents. 3) floor(N/2) + 1. Ex : 3 nœuds → quorum 2. 4) Lance la tâche en arrière-plan et retourne un task_id ; on peut suivre avec GET /_tasks/{id}. 5) hash(_id) distribue aléatoirement, custom routing force un shard cible — utile pour colocaliser des documents liés. 6) Applique automatiquement ce pipeline à chaque document indexé dans cet index. Timing : 10 min.

DQL — Dashboards Query Language (basics)

// Égalité sur keyword
category.keyword: "Electronics"

// Plage numérique
price >= 100 and stock > 0

// Wildcard (attention aux perfs)
name: *running*

// Négation
not in_stock: false

// Combinaisons
(category.keyword: "Books" or category.keyword: "Music") and price < 50
DQL vs Lucene : DQL = syntaxe lisible, pas de scoring, autocomplétion dans Dashboards. Lucene = requête full-text avec scoring, opérateurs booléens (+/-).
DQL est le langage par défaut dans Discover et les vizzes. Il est plus simple que Lucene : pas de scoring, pas de guillemets obligatoires pour les mots simples. Le toggle 'DQL/Lucene' se trouve à gauche de la barre de recherche. Timing : 5 min.

DQL avancé — nested, ranges, wildcards

// Champ imbriqué (nested ou objet)
attributes.color: "red"

// Plage de valeurs
price >= 50 and price <= 200

// Wildcard milieu de chaîne
name: *pro*

// Wildcard début de chaîne (plus lent)
name: *book

// Filtre sur date
indexed_at >= "2024-01-01" and indexed_at <= "2024-12-31"
⚠️ Wildcard en début/milieu de chaîne est lent sur haute cardinalité. Pour regex complexes → utilisez Lucene Query String en passant le toggle DQL → Lucene.
Les wildcards leading (commençant par *) sont les plus coûteux car OpenSearch doit scanner tous les termes de l'index inversé. En production, évitez-les sur des champs à forte cardinalité comme les IDs ou les descriptions. Timing : 4 min.

Lens — créer des visualisations drag & drop

Workflow Lens :

  1. Panneau gauche → champs disponibles
  2. Glisser vers zone X / Y / Color / Size
  3. Lens suggère automatiquement le meilleur viz
  4. Changer le type en 1 clic (barre → ligne → donut)
  5. Ajouter une 2ème couche (multi-series)

Formules avancées :

// % du total
count() / overall_sum(count()) * 100

// Ratio de deux métriques
sum(revenue) / count()

// Moving average
moving_average(count(), window: 7)
✅ Mode recommandé pour les apprenants — plus intuitif que l'ancien mode Aggregation.
Lens remplace progressivement l'ancien éditeur d'agrégations. Il est plus rapide, plus intuitif, et les formules permettent des calculs complexes sans écrire de DSL. Encouragez les apprenants à l'utiliser dans TP12. Timing : 6 min.

TSVB — séries temporelles avancées

Time Series Visual Builder — capacités :

  • Math entre séries : series_a / series_b * 100 → taux de conversion
  • Décalage temporel : Offset: 1w → comparer cette semaine vs la semaine précédente
  • Annotations : marquer des événements sur la timeline (releases, incidents)
  • Moving average / Percentile — built-in, sans formule
Cas d'usage : rates (req/s), ratios (succès/total), comparaisons temporelles. TSVB excelle là où Lens atteint ses limites.
TSVB est puissant mais plus complexe que Lens. À utiliser quand on a besoin de comparer deux séries, de calculer des taux, ou d'ajouter des annotations d'événements sur une courbe temporelle. Timing : 5 min.

Écosystème collecteurs

Les données viennent de partout

"OpenSearch est le moteur. Logstash, Data Prepper et Fluent Bit sont les tuyaux."

Transition après le TP12. Maintenant qu'on sait visualiser, il faut savoir comment faire arriver les données dans OpenSearch depuis le monde réel. Timing : 1 min.

Vue d'ensemble des collecteurs

  • Logstash — ETL mature, 200+ plugins, JVM, DSL config (Ruby). Migration de données, transformations complexes.
  • Data Prepper — OpenSearch-native, YAML, OpenTelemetry, container-first. Observabilité moderne.
  • Fluent Bit — <450KB, C, zéro dépendance, DaemonSet Kubernetes. Edge et conteneurs.
  • Beats — Filebeat/Metricbeat/Packetbeat, agents légers Go. Collecte ciblée par protocole.
💡 Pas de silver bullet — choisissez selon votre contexte d'infrastructure.
Les 4 grandes familles de collecteurs. En pratique dans les grandes organisations, on en voit souvent 2 ou 3 coexister : Fluent Bit pour les logs K8s, Logstash pour les migrations, Data Prepper pour l'observabilité OTEL. Timing : 4 min.

Data Prepper adopte une architecture similaire à Logstash mais en YAML. Le buffer joue le rôle de queue intermédiaire entre la source et le processor — en cas de pic de charge, les messages s'accumulent sans perte. Timing : 5 min.

Dans le TP, Data Prepper sera dans le docker-compose avec le reste de la stack. Les ports importants : 4900 pour la gestion (health check, métriques Prometheus, liste des pipelines), 2021 pour recevoir des données via HTTP POST. Timing : 5 min.

Data Prepper — structure du pipeline YAML

spacex-pipeline:                    # Nom du pipeline
  source:
    http:                           # Source : HTTP POST sur port 2021
      port: 2021
      path: /log/ingest

  buffer:
    bounded_blocking:               # Buffer in-memory avec limite
      buffer_size: 1024
      batch_size: 256

  processor:                        # Chaîne de transformations
    - date:
        from_time_received: true
        destination: "@timestamp"
    - mutate_event:
        add_entries:
          - key: source
            value: spacex-api

  sink:                             # Destination
    - opensearch:
        hosts: ["https://opensearch-node1:9200"]
        index: spacex-launches
        username: admin
        password: "${OS_PASSWORD}"
        insecure: true
Lisez le YAML ligne par ligne avec les apprenants. Insistez sur la structure hiérarchique : pipeline-name → sections source/buffer/processor/sink. La variable ${OS_PASSWORD} est injectée via les variables d'environnement Docker. Timing : 5 min.

Data Prepper — Processors

ProcessorUsage

Exemple SpaceX :

processor:
  - date:
      match:
        - key: date_utc
          patterns: ["yyyy-MM-dd'T'HH:mm:ss.SSSZ"]
      destination: "@timestamp"
  - mutate_event:
      add_entries:
        - key: source
          value: spacex-api
Le processor date est crucial pour que le champ @timestamp soit correctement parsé — sans ça, les visualisations temporelles ne fonctionnent pas. Le processor obfuscate est votre allié RGPD. Timing : 6 min.

Data Prepper — Sink OpenSearch

sink:
  - opensearch:
      hosts: ["https://opensearch-node1:9200"]

      # Index avec date dynamique
      index: "spacex-launches-%{yyyy.MM.dd}"

      # Authentification
      username: admin
      password: "${OS_PASSWORD}"

      # TLS auto-signé (dev uniquement)
      insecure: true

      # Idempotence : utiliser l'ID SpaceX comme _id
      document_id: "%{id}"

      # Taille du batch bulk
      bulk_size: 100

      # Créer l'index si absent
      index_type: custom
⚠️ insecure: true = ignore le certificat TLS. À remplacer par cert en production.
Le document_id avec l'ID SpaceX garantit l'idempotence : indexer deux fois le même lancement ne crée pas de doublon. Le bulk_size de 100 est un bon compromis performance/mémoire pour de petits volumes. Timing : 5 min.

Pousser les données depuis l'API SpaceX :

# Récupérer + filtrer + envoyer
curl -s https://api.spacexdata.com/v4/launches \
  | jq '[.[] | {
      id,
      name,
      date_utc,
      success,
      flight_number,
      rocket,
      launchpad,
      details
    }]' \
  | curl -XPOST \
      http://localhost:2021/log/ingest \
      -H "Content-Type: application/json" \
      -d @-

# Vérifier l'ingestion
curl -s http://localhost:9200/spacex-launches/_count \
  | jq '.count'
La commande curl + jq est le pattern clé de ce TP. On récupère tous les lancements de l'API SpaceX (format tableau JSON), on filtre les champs utiles avec jq, puis on pipe directement vers l'endpoint HTTP de Data Prepper. Pas de Python3 nécessaire. Timing : 8 min.

Grok patterns — parser des logs structurés

Patterns intégrés utiles :

  • COMBINEDAPACHELOG — logs Apache/nginx complets
  • COMMONAPACHELOG — sans Referer/User-Agent
  • SYSLOG5424 — RFC 5424 syslog
  • TIMESTAMP_ISO8601 — dates ISO
  • IP, WORD, URI, NUMBER, GREEDYDATA

Pattern custom :

grok {
  match => {

  }
}
🛠️ Testez vos patterns sur grokdebug.herokuapp.com avant de les déployer.
Les patterns Grok sont des expressions régulières nommées. GREEDYDATA = .* (capture tout). En pratique, utilisez les patterns intégrés quand c'est possible et ne créez des patterns custom que pour des formats maison. Timing : 5 min.

On_failure handler — gestion des erreurs

⚠️ Sans on_failure : les événements en erreur de parsing sont rejetés silencieusement — vous perdez des données sans le savoir. 
filter {
  grok {
    match => { "message" => "%{COMBINEDAPACHELOG}" }
    on_failure {
      mutate {
        add_field => { "parse_error" => "grok_failed" }
        add_tag   => ["_grokparsefailure"]
      }
    }
  }

  # Router les erreurs vers un index dédié
  if "_grokparsefailure" in [tags] {
    mutate { add_field => { "[@metadata][index]" => "failed-ingestion" } }
  }
}

output {
  opensearch {
    index => "%{[@metadata][index]:-spacex-launches}"
  }
}
✅ Essentiel en production — jamais de pipeline sans on_failure.
Le pattern d'index fallback avec `:-` est une syntaxe Ruby : si @metadata[index] est vide, utiliser spacex-launches. Routing des erreurs vers un index dédié permet de les analyser et corriger sans perdre les données. Timing : 4 min.

Introduction de section. La gestion du cycle de vie est une des compétences les plus demandées en production OpenSearch. Sans ISM, les index grossissent indéfiniment jusqu'à remplir le disque. Timing : 1 min.

ISM — Index State Management

Définition : Plugin natif OpenSearch. Gestion déclarative du cycle de vie des index.
Policy : states + transitions + actions. Polling : toutes les 5 minutes.

API principales :

GET /_plugins/_ism/policies

# Statut d'un index
GET /_plugins/_ism/explain/spacex-logs-000001

# Attacher manuellement
POST /_plugins/_ism/add/spacex-logs-000001

Auto-attachement :

"ism_template": [{
  "index_patterns": ["spacex-*"],
  "priority": 100
}]

Tous les nouveaux index spacex-* reçoivent automatiquement la policy.

ISM remplace avantageusement les scripts cron de gestion manuelle des index. L'ism_template est la clé : on configure une fois, tous les futurs index sont gérés automatiquement. Timing : 5 min.

ISM — policy hot → warm → cold → delete

PUT /_plugins/_ism/policies/spacex-lifecycle
{
  "policy": {
    "description": "Cycle de vie SpaceX : 7j hot → 30j warm → 90j delete",
    "ism_template": [{ "index_patterns": ["spacex-*"], "priority": 100 }],
    "states": [
      {
        "name": "hot",
        "actions": [],
        "transitions": [{ "state_name": "warm", "conditions": { "min_index_age": "7d" } }]
      },
      {
        "name": "warm",
        "actions": [
          { "read_only": {} },
          { "force_merge": { "max_num_segments": 1 } }
        ],
        "transitions": [{ "state_name": "cold", "conditions": { "min_index_age": "30d" } }]
      },
      {
        "name": "cold",
        "actions": [{ "cold_migrate": { "timestamp_field": "@timestamp" } }],
        "transitions": [{ "state_name": "delete", "conditions": { "min_index_age": "90d" } }]
      },
      {
        "name": "delete",
        "actions": [{ "delete": {} }],
        "transitions": []
      }
    ]
  }
}
Lisez la policy état par état. HOT : aucune action, juste attendre. WARM : passer en lecture seule + force_merge pour réduire les segments (économise du CPU en lecture). COLD : migrer vers le stockage froid. DELETE : supprimer définitivement. Timing : 8 min.

Snapshots — principes et repositories

Principes :
  • Copie incrémentale (seuls les deltas)
  • Cohérent même pendant les écritures
  • Restore partiel (index par index)
  • Rename à la restauration possible
Repositories :
  • fs — Système de fichiers (dev)
  • s3 — AWS S3 (prod recommandé)
  • azure — Azure Blob Storage
  • gcs — Google Cloud Storage
RPO (Recovery Point Objective)
Quelle perte de données acceptable ? → fréquence snapshots
RTO (Recovery Time Objective)
Combien de temps pour restaurer ? → taille snapshots + débit réseau
⚠️ Toujours tester la restauration en staging ! Un snapshot non testé = pas de backup.
Les snapshots sont incrémentaux : seul le premier snapshot est complet, les suivants ne stockent que les nouvelles données. RPO/RTO sont des métriques SRE importantes. En prod, snapshots quotidiens sur S3 avec retention 30 jours est un bon standard. Timing : 6 min.

Snapshot Lifecycle Management (SLM)

// 1. Créer le repository filesystem (dev)
PUT /_snapshot/fs-backup
{
  "type": "fs",
  "settings": {
    "location": "/mnt/snapshots",
    "compress": true
  }
}

// 2. Créer la policy SLM — snapshot quotidien à 1h du matin
PUT /_plugins/_sm/policies/daily-backup
{
  "description": "Snapshot quotidien de tous les index",
  "creation": {
    "schedule": { "cron": { "expression": "0 1 * * *", "timezone": "Europe/Paris" } },
    "config": {
      "repository": "fs-backup",
      "indices": ["spacex-*", "products"],
      "include_global_state": false
    }
  },
  "retention": {
    "expire_after": "30d",
    "max_count": 30,
    "min_count": 5
  }
}

// 3. Vérifier le statut
GET /_plugins/_sm/policies/daily-backup/explain
SLM automatise entièrement la gestion des snapshots. La retention avec max_count:30 garantit qu'on ne gardera pas plus de 30 snapshots (évite de remplir le stockage). min_count:5 assure qu'on garde au minimum 5 snapshots même si ils sont vieux. Timing : 6 min.

Anomaly Detection

Le ML sans data scientist

"Et si votre cluster détectait lui-même les comportements anormaux dans vos données ?"

Random Cut Forest · Anomaly Grade · Confidence · Real-time

Introduction de section. Anomaly Detection est un des plugins les plus impressionnants d'OpenSearch. Il utilise Random Cut Forest, un algorithme ML non supervisé, pour détecter automatiquement les valeurs aberrantes sans avoir à définir des seuils manuellement. Timing : 1 min.

Random Cut Forest (RCF) — le modèle

Principe :
  • Arbres aléatoires construits sur les données
  • Point anomal = modifie significativement la structure de l'arbre
  • Non supervisé : pas de labellisation requise
  • S'entraîne sur l'historique, surveille en temps réel
Métriques de sortie :
  • anomaly_grade (0→1) : degré d'anomalie
  • confidence (0→1) : confiance du modèle
  • Grade > 0 : potentiellement anormal
  • Grade > 0.7 + confidence > 0.9 : alerte sérieuse
✅ Avantage clé : pas besoin de définir un seuil manuellement — RCF apprend la "normalité" de vos données.
Random Cut Forest est un algorithme développé par Amazon Research. Contrairement à une alerte classique à seuil fixe (alert if value > X), RCF s'adapte aux patterns de vos données : saisonnalité, tendances, cycles hebdomadaires. Timing : 6 min.

Créer un détecteur dans Dashboards

Étapes dans l'interface :

  1. Dashboards → Anomaly Detection → Create detector
  2. Nommer le détecteur + sélectionner index spacex-launches
  3. Champ à surveiller : flight_number, agrégation : count()
  4. Intervalle de détection : 1 month (adapter à la granularité)
  5. Shingle size : 8 (fenêtre glissante = 8 × intervalle)
  6. Lancer l'analyse historique (entraîne le modèle sur le passé)
  7. Activer la détection en temps réel
💡 Le shingle size contrôle la "mémoire" du modèle. Plus élevé = plus de contexte temporel, moins sensible aux pics ponctuels.
Montrez la création en live si possible. Le shingle size de 8 est la valeur par défaut recommandée. Pour des données mensuelles, ça représente 8 mois de contexte. L'analyse historique peut prendre quelques minutes selon le volume. Timing : 6 min.

Checklist production — sécurité

  • ✅ TLS transport (port 9300) + TLS REST (port 9200)
  • ✅ Certificats démo remplacés par CA interne ou Let's Encrypt
  • ✅ Mot de passe admin changé (exit la démo admin:admin)
  • ✅ RBAC avec principe du moindre privilège
  • ✅ DLS/FLS pour données PII et multi-tenant
  • ✅ Audit logs activés (FAILED_LOGIN, MISSING_PRIVILEGES, INDEX_EVENT)
  • ✅ Port 9200 derrière reverse proxy (nginx/traefik) — jamais exposé directement
  • ✅ cluster.initial_master_nodes supprimé après bootstrap initial
Ces 8 points sont le minimum non négociable pour passer en production. Le plus souvent oublié en pratique : supprimer initial_master_nodes après bootstrap (risque de split-brain), et remplacer les certs de démo (ils sont publics sur GitHub). Timing : 4 min.

Checklist production — performance & fiabilité

  • ✅ JVM heap = 50% RAM max, plafonné à 32 GB (compressed oops)
  • ✅ Shard < 50 GB, cible ~30 GB — éviter les shards trop gros ou trop petits
  • ✅ Replicas ≥ 1 en production — tolérance à la panne d'un nœud
  • ✅ ISM sur tous les index temporels — rollover + lifecycle automatiques
  • ✅ Snapshot quotidien vers S3 via SLM — retention 30 jours
  • ✅ Index Templates sur tous les patterns d'index
  • ✅ Alerte JVM heap > 75% (GC pressure)
  • ✅ Alerte disk > 80% (watermark low)
  • ✅ GET /_cluster/allocation/explain pour diagnostiquer Yellow/Red
La règle des 32GB heap est liée aux "compressed object pointers" de la JVM — au-delà, les pointeurs passent de 32 à 64 bits, ce qui augmente la consommation mémoire. Le disk watermark low (80%) déclenche le refus de nouvelles allocations de shards. Timing : 4 min.

Parent-Child

Quand la hiérarchie est inévitable

⚠️ AVERTISSEMENT

Join fields are RAM-intensive and should be avoided when possible.

Alternatives à considérer en priorité :

  • Dénormalisation — dupliquer les champs parent dans chaque enfant
  • Nested documents — pour les relations 1-N dans un même document
  • Join applicatif — plusieurs requêtes dans le code

Docs : https://opensearch.org/docs/latest/field-types/supported-field-types/join/
Référence : https://www.elastic.co/blog/managing-relations-inside-elasticsearch

Section optionnelle — abordez-la uniquement si vous êtes en avance sur le planning et si des apprenants ont des besoins de modélisation hiérarchique. Durée estimée : 20-25 min. Timing : 2 min pour ce slide d'intro.
OPTIONNEL

join field type — modélisation

Mapping :

PUT /spacex
{
  "mappings": {
    "properties": {
      "join_field": {
        "type": "join",
        "relations": {
          "rocket": "launch"
        }
      },
      "name": { "type": "keyword" }
    }
  }
}

Comparaison approches :

ApprocheAvantageInconvénient
DénormalisationSimple, rapideDuplication données
NestedAtomiqueUpdate = réindexer tout
Join fieldIndépendanceRAM + lent
⚠️ L'enfant DOIT avoir le même routing que le parent.
Le join field type crée une relation parent-enfant dans le même index OpenSearch. La contrainte de routing est critique : si l'enfant est sur un shard différent du parent, les requêtes has_child/has_parent retournent 0 résultat sans erreur. Timing : 6 min.
OPTIONNEL

Indexer des parents et des enfants

// 1. Indexer le parent (rocket Falcon 9)
PUT /spacex/_doc/falcon9?routing=falcon9
{
  "name": "Falcon 9",
  "manufacturer": "SpaceX",
  "join_field": {
    "name": "rocket"
  }
}

// 2. Indexer un enfant (lancement CRS-1)
PUT /spacex/_doc/launch_crs1?routing=falcon9
{
  "name": "CRS-1",
  "date_utc": "2012-10-08T00:35:00.000Z",
  "success": true,
  "join_field": {
    "name": "launch",
    "parent": "falcon9"
  }
}
⚠️ Erreur fréquente : oublier ?routing=falcon9 sur l'enfant → mauvais shard → 0 résultats sans message d'erreur.
Le routing manuel est la contrainte la plus piégeuse du join field. En production, intégrez toujours la vérification du routing dans vos tests d'intégration. Le parent_id peut être n'importe quelle valeur unique — ici on utilise "falcon9" pour la clarté. Timing : 5 min.
OPTIONNEL

has_child / has_parent queries

has_child — trouver fusées ayant des lancements réussis :

GET /spacex/_search
{
  "query": {
    "has_child": {
      "type": "launch",
      "min_children": 5,
      "score_mode": "avg",
      "query": {
        "term": {
          "success": true
        }
      }
    }
  }
}

has_parent — trouver lancements de fusées US :

GET /spacex/_search
{
  "query": {
    "has_parent": {
      "parent_type": "rocket",
      "score": true,
      "query": {
        "term": {
          "country": "US"
        }
      }
    }
  }
}
has_child et has_parent sont les deux requêtes clés du join field. has_child (depuis parent) : "donne-moi les parents qui ont des enfants correspondant à ce critère". has_parent (depuis enfant) : "donne-moi les enfants dont le parent correspond". min_children et score_mode permettent d'affiner la pertinence. Timing : 6 min.
OPTIONNEL

Quand utiliser — et quand éviter

✅ Utiliser quand :

  • Relation many-to-many vraie
  • Cardinalité très déséquilibrée
    (1 parent, 100k enfants)
  • Les enfants doivent être mis à jour indépendamment du parent
  • Le parent évolue séparément

❌ Éviter quand :

  • On peut dénormaliser facilement
  • Moins de 10 enfants par parent
  • Haute cardinalité + requêtes fréquentes
  • Performance critique
Alternatives recommandées : Nested fields · Application-side join · Dénormalisation
La règle pratique : si vous pouvez dénormaliser sans duplication excessive, faites-le — c'est toujours plus rapide. Le join field est un dernier recours pour des cas vraiment hiérarchiques avec des mises à jour indépendantes. Timing : 5 min.
